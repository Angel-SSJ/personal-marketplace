# Expressing supplied state, ownership, and dependencies

## Minimal distinctions for faithful writing

An action reminder represents selected work; a project outcome represents a finite multi-action result; Waiting For represents an expected result from someone else; a sequential item represents work dependent on an earlier step; an incubated possibility is not an accepted current commitment. These meanings help avoid miswording records, not run a second GTD process.

Use the state actually supplied or settled by the user/method. Do not force a waiting-result reminder into an imperative executable title or silently turn an outcome into a chosen action. When state is ambiguous, ask or flag it for GTD rather than decide actionability, move items among lists, or fabricate an executable predecessor.

## Waiting-result wording

Express the stated responsible person, expected deliverable, and accepted follow-up date clearly. For “Waiting for Sam's logo” with no date supplied, retain Sam and the logo; mark follow-up unresolved. Do not invent the delivery agreement, select a follow-up date, send a message, or mark downstream work ready.

The existing @Waiting For display denotes state, not a topical/context tag vocabulary. The selected execution system can represent that distinction without a mandated application or file format.

## Preserve facts

Owner unknown is not “me”. No reply is not necessarily late. A follow-up action and the downstream task are distinct; rewriting one does not resolve the dependency. Supplied ready/blocked state, project membership, or completion should not change during an expression edit. If the facts contradict the supplied label, surface the contradiction and request the deciding fact instead of silently replacing it.
