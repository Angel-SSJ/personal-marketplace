# Inbox and temporary Intake policy

## Scope and authority

This is the user's local workflow policy, not a fifth PARA category or a universal methodological rule. Paths are relative to the user's chosen storage root. 05-intake is the target profile; do not rename or migrate any older intake path without a separate authorized operation. Infer the relevant method from the user's goal; a person need not name a skill. Method references alone do not install or execute companions. Read an available specialist when its decision is needed; do not ask permission merely to select the relevant skill. Ask for missing intent or approvals actually required below.

## Structure

```text
05-intake/
  inbox/
  projects/<entity>/
  areas/<entity>/
  resources/<entity>/
```

inbox holds inputs whose destination is unresolved. The other category containers hold only packages with a known intended destination and a concrete incorporation dependency. Names inside angle brackets follow the local naming policy for verified entity folders; they do not create new entities. Several independent packages for the same entity may be grouped only as retrieval requires; distinguish their holds without mandatory nesting, filenames or metadata. Do not create empty trees as compliance work.

## Admission and retention tests

1. Capture an input temporarily when deciding its meaning/destination would interrupt capture, or when a genuine incorporation dependency prevents immediate filing. Selective capture may preserve an explicit exploratory interest without a current project.
2. Inspect the material and relevant existing entities to establish identity, actual contribution, existing equivalents, access and lifecycle. A matching filename is not proof of identity, duplication or usefulness. Unknown access yields provisional classification and a specific unresolved question.
3. If the home is known and incorporation is possible, file directly there. Being incomplete, unread, unsummarized, aesthetically unfinished or convenient to batch does not by itself justify retention. A needed validation must be concrete and material to correct incorporation, not an invented gate for every document.
4. A retained known-destination package needs an understood intended home, concrete hold reason, and observable exit condition. Use existing support or the conversation; no mandatory file, sections, schema, tags or registry. If these facts are missing, clarify them; do not portray the package as a valid indefinite hold.
5. Move independently useful components home when safe; hold the whole package only if splitting would damage validation, coherence or a real joint-delivery requirement. Preserve the association with remaining components.
6. When the exit condition is met, incorporate and verify. No arbitrary expiry, invented deadline or automatic deletion. If the dependency disappears or is no longer justified, reassess; do not keep a permanent parallel PARA tree.

## Classification and boundaries

An Inbox entry is unclarified; a held package is clarified enough to have a destination but cannot yet be incorporated. Someday/Maybe is a clarified uncommitted possibility, not an Intake holding category. Store its useful support in Resources or another justified home; do not create a fake Project. Tickler is a genuine future reconsideration trigger, not an arbitrary due date. Waiting For tracks an external expected result, responsible person and real follow-up; one's own unfinished work is not Waiting For. No inferred action is a new accepted commitment.

GTD owns actionability, outcomes, next actions, Waiting For, calendar/tickler and incubation. PARA owns support placement and lifecycle. CODE assesses knowledge usefulness and transforms selected material without requiring summarization. Inbox coordination follows the local admission/exit rules. task-writing may express known reminders; none of these states automatically becomes a tag or changes the task vocabulary.

## Entity matching and destinations

Search relevant existing Projects, Areas and Resources before proposing a new entity. Distinguish finite accepted outcomes, ongoing standards, and useful reference interests. Topic overlap alone does not make material project-exclusive. Prefer one useful canonical home and links for multiple relevant entities; do not silently create divergent copies or merge merely similar entities. Propose reuse or creation with evidence. New entity creation requires explicit confirmation; if the user's current instruction already explicitly authorizes that creation, do not ask again. This includes new named organizational containers, not incidental directories inside an already approved structure.

For existing Projects use assets for project-exclusive source material, docs for current editable work, drafts for scratches/superseded iterations and submissions for frozen final snapshots. Area standards and persistent records stay with the Area; finite multi-action deliverables need a real Project. Resources hold useful knowledge without requiring an obligation. Apply the local naming policy during authorized file/folder operations; do not impose arbitrary document contents.

For an archived destination, distinguish read-only historical lookup, adding historical evidence, reusable reference extraction and actual renewed work. No automatic reactivation or live edits in Archives. Propose the appropriate destination/lifecycle decision; preserve incoming evidence pending it when necessary. Existing archive policy governs authorized reactivation. A historical association is not proof that a new project exists.

## Safe incorporation and review

Within a request to organize a bounded scope, unambiguous moves to approved existing homes can proceed with actual access. Before moving, check source, destination, identity, collisions, links and record preservation. Never overwrite or delete without specific approval; an apparent duplicate is only a candidate. Prefer moves to uncontrolled copying; copying can be proposed when provenance or retention needs it. After moving verify destination contents and source disposition, preserve/repair affected references within authority, and report actual results, unresolved items and verification limits. If move or link repair fails, report partial state, preserve available data and do not claim completion. Read and inspect before any retry; do not blindly overwrite to roll back.

Review Intake during the existing weekly GTD review: unresolved captures, each hold's continuing reason and exit condition, dependencies/follow-up, newly satisfied exits and broken support links. A file in Intake must not hide an active obligation. Preserve genuine reminders independently of file location. Use bounded checks during ordinary work; expand audits only for recurring failure. Age is a signal for reconsideration, never proof of uselessness. No automatic purge.
