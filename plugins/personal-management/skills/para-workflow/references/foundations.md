# PARA foundations

## Concepts and categories

PARA is Tiago Forte's actionability-based organization method for supporting information. It answers where material is useful, rather than imposing an exhaustive taxonomy of everything a person knows.

| Category  | Defining condition                                                                  | Example                            | Exit or change condition                                              |
| --------- | ----------------------------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| Projects  | A currently committed finite effort with a specific outcome and recognizable finish | Submit a reimbursement claim       | Outcome completed, commitment paused, canceled, or redefined          |
| Areas     | An ongoing responsibility with a standard worth maintaining                         | Maintain personal finances         | Responsibility ends, changes owner, or changes scope                  |
| Resources | A topic or reusable reference with continuing interest or potential utility         | Research on negotiation techniques | Recruited into active use, no longer useful, or no longer of interest |
| Archives  | Inactive support retained for history, retrieval, or reuse                          | Materials from a finished event    | Reactivated by current use; deletion is a separate retention decision |

A project outcome describes a finishable change; an Area standard describes a continuing acceptable condition. An interest has no implied obligation. Archives is a change of active status, not a judgment of quality or a synonym for trash.

An inbox is a temporary intake state before classification. It is not a fifth permanent PARA category or a place to hide undecided work indefinitely. Choose a reliable way to revisit incoming material without requiring filing at the instant of capture.

## Principles

1. **Actionability first.** Prefer the current project that uses the material, then an ongoing responsibility, then a useful topic, then inactive storage.
2. **Minimum useful structure.** General PARA adds subdivisions when retrieval or collaboration needs them. This user's storage profile explicitly fixes four project role directories; apply those and keep further nesting minimal.
3. **Current commitments before historical cleanup.** A new working system can start with current work while legacy material remains recoverable.
4. **Coherence across surfaces.** The same project or responsibility should retain its meaning across information and action systems. This user's profile fixes the four parent directory names across relevant storage surfaces; it does not require identical contents, document labels, or a project-name format.
5. **Forgetting without losing.** Remove inactive material from the active view while preserving retrieval and obligations.
6. **Structure at the moment of need.** A useful item need not receive elaborate tags, layers, or classification before it can be used.
7. **Net benefit.** Maintenance should save more attention than it consumes. Retrieval success and useful output matter more than visual tidiness.

## Conditions and decision rules

| Question                                         | If yes                                               | If no                                     |
| ------------------------------------------------ | ---------------------------------------------------- | ----------------------------------------- |
| Does a real active project need this material?   | Associate it with that project                       | Check an Area                             |
| Does it support maintaining an ongoing standard? | Associate it with that Area                          | Check a Resource                          |
| Is it useful reference or a continuing interest? | Associate it with a Resource                         | Consider inactive retention or not saving |
| Does it carry an unresolved commitment?          | Capture/clarify that commitment in the action system | Filing can proceed independently          |
| Does more than one active context need it?       | Choose a useful primary home and links or references | Keep the single useful home               |

When a project and an Area both apply, current project use normally wins for that project's support. A canonical reference serving many contexts may stay in its stable home with a project link. Choose based on retrieval and ownership, not an absolute ban on duplication. Avoid divergent copies without an intentional reason.

## Theoretical status

These are practitioner concepts and heuristics, not formal mathematical theorems. The four-category model is a design framework, not a proven taxonomy of every conceivable artifact. Claims that simpler structure reduces friction are practical hypotheses to assess through the person's retrieval and upkeep experience.

Personal reports about note counts, seconds per file, tagging costs, or review duration do not establish universal thresholds. Do not impose a note-count limit, exact time saving, compulsory tagging policy, or fixed review duration as a theorem. The integration and audit references introduce local operating policies explicitly; those policies are not additional canonical PARA laws.

## Lifecycle

Support moves from captured/unclarified to active Project, Area, or Resource use, then to inactive retention when its use changes. It may move back into active use. Category is contextual and reversible, not an immutable property of a file. Project completion is determined by its outcome and remaining commitments, not by whether its container appears tidy.
