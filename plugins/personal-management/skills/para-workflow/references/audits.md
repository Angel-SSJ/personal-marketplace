# PARA audits and preventive checks

## Purpose and scope

An audit diagnoses an observed retrieval, classification, lifecycle, or action-boundary problem and checks this user's explicit storage profile. That profile is local policy, not a universal PARA template. The audit does not grade a person's neatness, project-name format, filename choices, root-file existence, or document sections/content.

Choose a bounded scope from actual friction: one stalled project, recent incoming material, a changed responsibility, or a small representative sample. State what was inspected and what remains unknown. Do not extrapolate a sample into a claim that the whole system is clean.

## Levels of intervention

These levels are local operating policy, not canonical PARA rules.

- **In-use check:** When touching an item, verify current purpose and retrieval; fix the local problem.
- **Focused audit:** When the same problem recurs or a project changes state, inspect its surrounding materials and action handoffs.
- **System audit:** When focused repairs fail, several Areas are affected, or a major transition changes responsibilities, inspect category boundaries, sources of truth, and lifecycle across the agreed system.

Integrate checks into existing reviews. Escalate because of evidence of recurrence, missed obligations, or material retrieval failures; a large item count alone is not a failure trigger.

## Audit questions and observable evidence

| Question                                                | Evidence to seek                                                                                      | Repair if a defect is confirmed                                                                               |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Are active projects real and finite?                    | Actual commitment and completion condition                                                            | Separate ongoing responsibility or uncommitted interest                                                       |
| Can current support be found where work happens?        | A retrieval attempt or user-reported concrete failure                                                 | Correct the relevant placement/link                                                                           |
| Are responsibilities distinguished from interests?      | A standard the person maintains versus optional future use                                            | Reclassify the ambiguous case                                                                                 |
| Are completed/paused materials out of active attention? | Confirmed status, with remaining obligations accounted for                                            | Archive inactive support and preserve reminders                                                               |
| Are action reminders visible outside reference storage? | Trace a real obligation to an action/waiting/calendar reminder                                        | Capture the missing reminder                                                                                  |
| Do surfaces refer to the same current outcome?          | Identity, status, owner, and links                                                                    | Align meaning and current state                                                                               |
| Does maintenance earn its cost?                         | Repeated searches, missed work, and upkeep burden                                                     | Remove unnecessary maintenance or target one recurring friction                                               |
| Does storage follow the confirmed profile?              | Parent paths, the project's four sibling role directories, actual work state, and archive destination | Propose a bounded role/destination correction without imposing file naming/content                            |
| Are frozen records preserved?                           | A proposed write into submissions or Archives, or a replaced delivered snapshot                       | Resume editable work in docs, preserve the prior record, and reactivate archived work before editing          |
| Is every active project container linked to work?       | A real Next Action or Waiting For, not just a future trigger                                          | Clarify a missing route forward or explicit nonactive state without inventing an action or dropping a promise |

No evidence available means unknown, not passed. Do not create a defect merely because an item could have been filed elsewhere.

## Finding format and prioritization

For each finding give: observed evidence; affected scope; method distinction; practical consequence; smallest repair; how to verify it; and a recurrence trigger. Mark inference separately from observation.

Fix lost obligations and inaccessible active support first, then repeated friction, then optional refinements. Severity follows effect on work, not the number of messy containers. For example: an action hidden in an archived folder risks a missed payment; an optional alternate Resource arrangement is a preference.

## Closure and prevention

Retest the original failure: retrieve the support, follow the action link, or confirm a lifecycle transition. Record whether the change was proposed, executed, and verified. Keep one lightweight cue at the failure point, such as checking remaining obligations when closing a project. Re-audit only when the cue fails, the issue recurs, or the context materially changes.

An audit can conclude that no change is justified. Give the evidence and limits, then return to the person's work.
