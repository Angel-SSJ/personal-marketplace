# PARA operations and recovery

## Starting from a cluttered system

1. Identify actual active outcomes and ongoing responsibilities from the person's commitments. Do not derive a project list solely from existing folder labels.
2. Apply the confirmed parent paths and role directories in [storage architecture](storage-architecture.md). For existing storage, distinguish a profile mismatch from a methodological defect and propose a bounded migration rather than silently renaming/moving material.
3. Make current support retrievable using the four-role project layout where a supported project exists. A GTD project with no supporting material does not need an empty project container.
4. Keep legacy material accessible while extracting only what current work needs. A recoverable inactive holding collection is an option, not permission for a bulk move.
5. Connect action reminders to relevant support and set a manageable review habit.

If the person wants a clean-slate migration, inspect scope, ownership, retrieval, shared links, and retention needs before proposing moves. Preserve an original-location mapping or other practical recovery path. In an advice-only session, describe the steps without claiming a migration occurred.

## Daily classification pipeline

Input → clarify purpose → check active project → check Area → check Resource → retain inactive or decline capture → preserve any action reminder → check retrieval.

For each ambiguous item, ask where the person would look when doing the work. If two categories remain plausible, explain the deciding fact and use a reversible recommendation. Within a project, route current editable work to docs, superseded/scratch iterations to drafts, final frozen artifacts to submissions, and project-exclusive source material to assets. Do not require inspection of the document's internal sections to approve its category. The user can supply its purpose and current use.

For a bounded batch, process the items relevant to today's work first. Keep unresolved items visible for later clarification rather than inventing categories to make an inbox look empty. A filed item can still generate an action; filing is not task completion.

## Project lifecycle pipeline

| State/event               | Information decision                                                   | Commitment handoff                                                               |
| ------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Idea under consideration  | Keep useful reference without declaring an active project              | Incubate the potential commitment                                                |
| Outcome committed         | Gather or link only needed support                                     | Define outcome and next visible action                                           |
| Work active               | Keep relevant support accessible; remove irrelevant distraction        | Update actions and waiting items as reality changes                              |
| Work blocked or delegated | Keep support available when work is still active                       | Track dependency, owner, and review/follow-up trigger                            |
| Explicitly paused         | Move inactive support out of the active view if useful                 | Record pause and reactivation/review condition; do not silently drop obligations |
| Outcome complete          | Check loose ends, preserve reusable material, archive inactive support | Close or transfer remaining actions explicitly                                   |
| Outcome canceled          | Preserve only useful/required history                                  | Renegotiate and close affected commitments                                       |
| Outcome reactivated       | Retrieve relevant support and verify its currency                      | Reconfirm commitment and current next action                                     |

Archiving a project's material does not complete the project in the action system. If a launch is delivered but a supplier payment remains, determine whether that obligation is part of completion. Either keep the project active or transfer the payment into an explicit tracked commitment before archiving its support. Do not decide that scope question from the folder alone.

## Maintenance without repeated reorganization

During use, fix a misplaced item when it causes friction. During the existing Weekly Review, check supported Projects and their Next Action/Waiting For linkage. Check Area standards monthly, Resources on reuse/as needed with optional quarterly hygiene, and archive retention annually as detailed in the storage architecture. Broader audits are driven by recurring failure, not added as a separate heavy routine for every category.

For cross-surface drift, establish which commitment/outcome is current, then align its references and status. Do not copy entire structures blindly. Shared support may have different ownership and access needs; changes should respect those relationships.

## Correction patterns

| Symptom                                               | Likely issue to verify                  | Small useful correction                                                          |
| ----------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| Health never finishes                                 | An ongoing Area is treated as a project | Keep Health as responsibility; identify only genuinely committed finite outcomes |
| Research unrelated to current work dominates Projects | Interest has become false commitment    | Reclassify useful material; renegotiate any claimed action separately            |
| Active view contains years of completed work          | Archival transition omitted             | Close/transfer obligations and archive one confirmed inactive project            |
| Actions are hidden in reference material              | Information/action boundary failed      | Capture visible reminders with support links                                     |
| Finding one item requires exploring many branches     | Structure exceeds retrieval needs       | Simplify the path or add a useful link where the friction occurs                 |
| Several copies contradict one another                 | No clear canonical reference            | Identify owner/current version; link intentionally before retiring duplicates    |

## Worked example

The person has fifteen minutes, thousands of old notes, Health listed as a project, and an apparently finished launch with a payment question. Start by distinguishing Health's ongoing standard from any finite health outcome. Retrieve only today's needed support. Clarify whether launch closure includes the payment, and capture or transfer the remaining obligation visibly. Leave the historical notes recoverable. Finish by testing whether the needed support can be found again. The profile fixes parent/role directory names, while project names and memo formats remain unrestricted.

## Stop conditions

Stop the batch when the agreed scope or available time is reached; report remaining ambiguity. If there is no evidence of retrieval or commitment friction, a structural preference alone does not justify a redesign. Never describe proposed moves as executed changes.
