# PARA workflow

Place support where it is useful now while keeping actual obligations visible. A folder or archive transition does not create, complete or cancel a commitment.

Read the local [system contract](references/system-contract.md), [foundations](references/foundations.md), [storage architecture](references/storage-architecture.md) and [naming policy](references/naming-policy.md). Use [operations](references/operations.md), [Intake policy](references/intake-policy.md) and [integrity cases](references/integrity-matrix.md) for the affected operation; [audits](references/audits.md) for review. Another skill or external research document is unnecessary.

## Recipe

1. Infer explain, coach, operate, correct or audit mode. Bound the material, current purpose, accepted outcomes/standards, relevant identities and storage surface. Use existing evidence before asking; resolve only missing facts that change placement or lifecycle.
2. Classify by current use: active finite Project → ongoing Area responsibility → useful Resource interest → inactive Archive. Unclarified inputs and genuinely blocked incorporation follow Intake. Topic similarity alone does not establish exclusive ownership or a new entity.
3. Verify existing entity and destination before creating anything. Keep one canonical home with links for other contexts. Apply global local naming during authorized file/folder operations; preserve technical/frozen exceptions and useful established subdivisions.
4. For a supported active Project establish a real Next Action or Waiting For reminder and accepted planning horizon; do not invent a deadline or action to satisfy structure. A project without support needs no folder. Waiting work can remain active; deliberately paused/future-trigger-only support requires a considered lifecycle decision, never silent reclassification.
5. Before archive/retirement, inspect completion evidence and remaining promises, dependencies, Goal contributions and access. Preserve or renegotiate obligations in the action system. Move inactive projects intact into the verified archive category; archive lookup alone does not reactivate them.
6. Check collision/link impact before bounded changes. Verify destination, source disposition, frozen records and affected operational pointers. On partial failure preserve success, inspect actual state and retry only pending steps. Report coverage and unresolved decisions accurately.

## Quick reference

| Material                               | Home                                                   |
| -------------------------------------- | ------------------------------------------------------ |
| Current editable work                  | `01-projects/<project>/docs`                           |
| Scratch/superseded work                | Project `drafts`                                       |
| Frozen delivered snapshots             | Project `submissions`                                  |
| Project-exclusive sources              | Project `assets`                                       |
| Ongoing standards / reusable interests | Verified `02-areas/<area>` / `03-resources/<resource>` |
| Inactive project                       | `04-archives/01-projects/<project>` intact             |

## Example and common mistakes

After verified closure and obligation review, archive `01-projects/launch` at `04-archives/01-projects/launch`, preserving its four role folders. Current editable `analysis-launch.xlsx` belongs in `docs`; an external source belongs in `assets`. Keep a legitimate `personal/private` subdivision. Verify destinations for retired Areas/Resources rather than inventing archive categories. Do not flatten useful structure, edit frozen submissions, create empty compliance trees or treat age/100% progress as proof of inactivity or completion. Audit alone authorizes findings, not moves.
